# Justificación de las Decisiones Arquitectónicas — v1.0

El proyecto utilizará inicialmente una **arquitectura cliente-servidor organizada por capas** (Presentación → Lógica de negocio → Acceso a datos → Base de datos), combinada con una **organización modular** por dominio funcional (Usuarios, Mascotas, Solicitudes, Seguimiento, Notificaciones). Se considera adecuada porque el sistema tiene responsabilidades claramente diferenciables (mostrar mascotas, gestionar solicitudes, dar seguimiento a su estado) y porque permite que cada módulo evolucione de forma independiente sin afectar a los demás. Las responsabilidades se separan así: la **capa de presentación** (React) se encarga únicamente de mostrar las pantallas y capturar las interacciones del usuario; la **capa de lógica de negocio**, dentro de la API REST (Node.js + Express), valida reglas y coordina cada módulo (por ejemplo, que solo el administrador pueda aprobar una solicitud); y la **capa de acceso a datos**, mediante repositorios, es la única que se comunica directamente con la base de datos (MongoDB), evitando que el resto del sistema dependa del motor de base de datos elegido. El sistema **sí utilizará una API REST** como punto único de comunicación entre el cliente web y el servidor: cada módulo expone sus propias rutas (`/api/usuarios`, `/api/mascotas`, `/api/solicitudes`), lo que mantiene una correspondencia directa y trazable entre cada requisito funcional, su pantalla y el componente técnico responsable de implementarlo.
